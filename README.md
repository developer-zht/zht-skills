# zht-skills

个人 skill 合集，用于 Claude Code 及其他智能体编码工具。

## 问题所在

让 AI 直接改项目源码，有两个绕不开的麻烦。

**一是改动不可控。** 你只想让它加一个函数，它顺手"改进"了旁边的注释、调整了格式、
重构了一段它觉得不够优雅的代码。diff 里混进一堆你没要求的东西，审查成本随之上升，
而漏看一行就可能引入回归。

**二是产出无处安放。** 分析、设计方案、实验实现这些中间产物往往比最终代码更有价值，
但它们要么污染源码树，要么散落在临时目录里，下次会话就找不回来了。

常见的应对是事后审 diff。但审查成本随改动量线性上升，而且它是补救，不是预防。

## 解决方案

换一个角度：不去审查它改了什么，而是**从一开始就限制它能写到哪**。

| 能力   | 范围                                           |
| ------ | ---------------------------------------------- |
| 读     | 整个项目，不受任何限制                         |
| 写     | 只有 `<模型名>-workspace/` 一个目录            |
| 改源码 | 不直接改 —— 贴出完整内容和可执行命令，由你落盘 |

`<模型名>` 随工具而定：`claude-workspace/`、`codex-workspace/`、`gemini-workspace/`。
同一个项目下不同工具各占一个目录，互不干扰。

源码树因此始终只读，而 AI 仍然能自由产出。每一次对源码的改动都要经你的手，
但**你不需要逐行审查它的全部工作**——因为它的工作全部落在一个你随时可以整个删掉的目录里。

## 包含的 skill

### `writing-to-isolated-workspace`

约束智能体的写入范围，把产出集中到项目内一个隔离工作区。

**默认状态**在每个新会话的第一轮自动生效，不需要你开口，也与项目里有没有文件、
有没有 `git init` 无关：读整个项目，写只进 `<模型名>-workspace/<主题>/`。
子目录名你指定就用你的，不指定由模型自取；只标主题，不重复模型名前缀。

**开场就把话说明白。** 每个会话第一轮，模型都要声明当前的写入权限——**默认状态下也要说**。
第一次在某个项目对话时给完整版：不光报当前值，还要列出**每一项还有哪些选择**、
**怎么改**、**不选或只选一半会怎样**。之后每次只用一行报状态。

只给当前值等于没说——用户看得懂字面，却不知道自己能不能改、怎么改、不管它会怎样。

**两项分开调，互不牵连。**

| | 回答什么 | 取值 |
| --- | --- | --- |
| ① 我能写哪些路径 | 写入范围 | 只写 `<模型名>-workspace/` ／ 你指定的目录 ／ 整个项目 |
| ② 这个设定管多久 | 有效期 | 只管这次对话 ／ 长期，新开对话继续沿用 |

任意组合都合法，**没有级别高低**。"长期 + 只写 workspace"和"只管这次 + 整个项目"
是两种不同的东西，不是一个的强弱版本。你只说了一项，另一项**维持原样**——
模型不替你推断，也不顺手一起改。

这一点是踩过坑才写进去的：早先的版本用 `global` / `local` 描述有效期，结果连设计者本人
都把它读成了写入范围，一句"改成 local"两边理解完全不同。所以规则里明令**禁用**
`global`、`local`、"提权"、"作用域"这几个词——它们无法自解释，还会把两项混成一项。

**放松要确认，收紧不必。** 你把权限模式调宽松，模型不会当作"可以随便写了"——
改模式常常只是不想被确认打断，或者人不在电脑前，这跟放开写范围是两回事，它会先问一句。
反过来调严格则不必打扰你，它自行退回。口头收窄和工具模式打架时，它提醒你决定；
你没表态，下一轮自动退回最严格。

**一条不依赖检测的兜底。** 有些权限模式在工具层自动放行，模型收到的返回值和"你逐条点了同意"
一模一样，分辨不出来。所以规则里写死了：每次要写工作区之外的文件之前，先自查这一轮的
写入范围是谁给的、有效期到什么时候、还有没有效——答不上来就按默认状态办。

完整规则见 [skills/writing-to-isolated-workspace/SKILL.md](skills/writing-to-isolated-workspace/SKILL.md)。

## 安装

**选项 A：插件市场（推荐）**

```
/plugin marketplace add developer-zht/zht-skills
/plugin install zht-skills@zht-skills-marketplace
```

装完在你所有项目中可用。

**选项 B：软链单个 skill**

```bash
git clone https://github.com/developer-zht/zht-skills.git
ln -s "$(pwd)/zht-skills/skills/writing-to-isolated-workspace" ~/.claude/skills/writing-to-isolated-workspace
```

只装这一个 skill，且改动仓库文件后立即生效，适合边用边改。

## 如何判断它在起作用

- **`git status` 始终干净** —— 项目源码里不出现你没要求的改动
- **产出集中可寻** —— 分析、方案、实验代码都在 `<模型名>-workspace/` 下，一个目录看全
- **改源码前你先看到内容** —— 收到的是完整代码块加一条可执行命令，而不是"我已经改好了"
- **随时可以推倒重来** —— 不满意就删掉对应的子目录，源码毫发无损
- **开场就报权限** —— 每次都告诉你现在能写哪、管多久，而不是等你踩到才发现
- **放宽时它会追问** —— 你没说清的那一项它不替你填，而不是默认往大了理解

## 权衡说明

这套规则倾向于**可控而非省事**。

代价是明确的：每一次需要改源码，都要多一轮"贴内容 → 你执行命令"的往返，改一行也不例外。
赶时间的时候会觉得啰嗦。放宽权限本身也要多一次确认。

适合的场景：你在意源码的每一行改动，或者项目已有一定体量、回归成本高。
如果是从零起步的原型，直接放开写可能更快。

当轮明确说"你帮我改"可以一次性豁免，但豁免不延续到下一轮。
要长期放开，把两项一起说清楚即可，比如"整个项目，长期"。

## 设计原则

**仓库里的 SKILL.md 只放普适规则和大多数人的合理默认；个人偏好留在自己的 memory 里，
由 memory 覆盖默认值。**

往 skill 加规则前先问一句：这是大多数人都想要的，还是只是我自己的习惯？
后者不进仓库。两者不冲突——它们是两层：仓库给公共默认，memory 给个人覆盖。

举个例子：SKILL.md 规定"每个对话开始询问是否要把写盘内容誊抄进对话框，不答则默认不誊抄"。
如果你就是每次都要誊抄，那是你的偏好，写进你的 memory 让它覆盖默认值，而不是改仓库。
